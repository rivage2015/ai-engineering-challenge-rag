# ストリーミング抽出・再開機能 v0.4

## 目的

大規模XLSXで中間JSONLが約179MBになったため、EvidenceとRelationを全件メモリへ
保持する方式を廃止し、ファイル単位で安全に中断・再開できる基礎抽出器へ更新した。

質問、案件名、record ID、正解候補による処理分岐は追加していない。

## 保存構造

```text
output/
  build-state.json
  build.lock
  documents.jsonl
  evidence.jsonl
  relations.jsonl
  shards/
    doc_<id>.documents.jsonl
    doc_<id>.evidence.jsonl
    doc_<id>.relations.jsonl
```

抽出中は、1つの原本に対応する3種類の一時シャードへ1行ずつ書く。
ファイル処理が終わった時点で`fsync`後に原子的に確定し、その後に
`build-state.json`を原子的に更新する。

全入力が終端状態になった場合のみ、入力相対パス順でシャードを結合し、
3種類の統合JSONLを作成する。

## チェックポイント

`build-state.json`は次を保持する。

- 抽出器名とversion
- 原本ルート
- 全入力相対パス
- ビルド全体の状態
- 抽出時刻
- ファイルごとの原本SHA-256
- Document IDと抽出状態
- シャードごとの相対パス、SHA-256、サイズ、レコード数

再開時に次の条件をすべて満たすファイルだけをスキップする。

1. 原本SHA-256が一致する。
2. 抽出状態が`success`、`partial`、`deferred`のいずれかである。
3. 3種類のシャードが存在する。
4. シャードのサイズとSHA-256がチェックポイントと一致する。

失敗ファイル、原本変更、シャード欠損・破損は再処理対象になる。

## 安全性

- `fcntl.flock`により、同じ出力先への同時ビルドを拒否する。
- 新規実行では空でない出力先を拒否する。
- 出力先が原本ルート内にある場合は拒否する。
- 再開時は、原本ルート、抽出器version、入力一覧の不一致を拒否する。
- 同一入力の重複指定は処理前に除去する。
- `--max-files`で処理を区切った場合、統合JSONLを作らず`in_progress`として残す。
- 全入力が終わるまで、部分的な統合JSONLを完成品として公開しない。

## 中断・再開検証

DOCX、XLSX、PPTX、PDF各1件、合計4件で確認した。

1. `--max-files 2`で開始した。
2. 2件分のシャードとチェックポイントだけが作られた。
3. 統合JSONLが存在しないことを確認した。
4. `--resume`で再開した。
5. 完了済み2件をスキップし、残り2件だけを処理した。
6. v0.3では4 Document、436 Evidence、436 Relationを生成した。
7. ID、内容ハッシュ、原本ハッシュ、親子参照、Relation端点の検証に合格した。

完了後に再度`--resume`した場合は4件すべてをスキップし、統合結果のSHA-256も
変化しなかった。

```text
documents.jsonl  7d9e180392d3991555dfe7deb4b88fb7939368cddd263511cb064f6847d7e179
evidence.jsonl   6aab5966cc85d44288b21fd464f22704ae85263726c2cbefde68724080b9bfaa
relations.jsonl  4bad7fa1a607315c0dbdede669efc8be334252a4e1f157e3e975c09ea95089c0
```

## DOCX文書順序と節文脈 v0.4

DOCXの段落と表を別々に列挙せず、本文XMLの出現順で逐次抽出する。
段落と表の`native_properties.body_order`を記録し、表には直前の見出し文字列と
Evidence IDを保持する。見出しと表の間には、決定的な
`structural/section_contains`関係を追加する。

代表4形式では4 Document、436 Evidence、437 Relationを生成し、整合性検証に
合格した。同一時刻・同一入力の再抽出で、統合JSONLとビルド状態が
バイト一致した。Evidence IDは変更せず、検索層で親見出しを参照できる。

## 大規模XLSX検証

4シート、130,438非空セル、2ピボット、9グラフEvidenceを持つXLSXを処理した。

| 指標 | 旧v0.2 | 新v0.3 |
|---|---:|---:|
| Evidence | 130,453 | 130,453 |
| Relation | 130,453 | 130,453 |
| ピーク常駐メモリ | 708,460,544 bytes | 434,012,160 bytes |
| 抽出失敗 | 0 | 0 |

ピーク常駐メモリは274,448,384 bytes、約38.7%減少した。
残るメモリの大部分は、openpyxlがワークブックを読み込むために使用する。

## 現時点の境界

- 統合JSONLと再開用シャードを両方保持するため、完了後のディスク使用量は増える。
- 整合性検証器は現在もJSONLを全件メモリへ読み込む。
- XLSX自体の読み込みはopenpyxlの通常モードで、ブック全体をメモリへ展開する。
- 複数マシンから同じネットワークファイルシステムを共有する場合のロックは未検証。

## 次の工程

検索層ではセルEvidenceを直接すべて投入せず、原本Evidenceから次の検索単位を
機械的に派生させる。

- ワークシート概要
- 連続した表領域
- ヘッダー付き行
- 数式と参照元をまとめた単位
- スライド・ページ・段落の検索用テキスト単位

原本事実層は変更せず、検索用派生層に元Evidence IDを必ず残す。
