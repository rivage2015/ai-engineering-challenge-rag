## 1. 目的と今回の境界

「選んだ資料に普通の言葉で質問すると、本文・表に書かれた内容を、実用的な時間で、根拠付きで教えてくれる」ことを第一目標にする。精度を犠牲にした高速回答ではなく、質問に不要な重い読取りを初回から一律に行わないことで待ち時間を減らす。

ユーザーが確認した優先順位：必要な資料の選択 → 本文・表の読取と関係の保持 → 通常検索を基本とし、必要な関係補完を経た根拠付き回答。画像精読は必要な場合の補助とする。既存QFの原文束・出典関係の補佐は初回回答前に保持し、回答後へ移す指示とは解釈しない。資料は特定業務へ特化しない。

依頼根拠：「精度は割と重要」「スピードが遅くなりすぎない」「今までやってきたことを素材として使いつつも、新しくリファインする」「計画立てて」。今回変更するのは本計画書だけ。既存の未コミット差分、原資料、索引、CONFIG、配布app、モデル、既存計画・テストは変更しない。commit/pushなし。

AGENTS.md／controlled-execution-plan v1.8の保護条項は維持する。本案は従来の全画像先行読取やV1範囲と異なる提案を含むため、自動的に承認済み計画へ昇格しない。旧実験を再開しない。

## 2. 残す資産と変える部分

| 項目 | 方針 |
| --- | --- |
| Word・Excel・PowerPoint・文字PDFのReader | 再利用。本文、見出し、表の対応、ページ／セル／スライド位置を保つ |
| 検索・ローカルGemma・原文束・既存グラフ補佐 | 再利用。新しい回答器やモデル比較からやり直さない |
| 原本保護、版確認、根拠照合、既存監査、途中失敗の説明 | 維持。高速化のために削除しない |
| 毎回すべてのPDFページを画像化してOCR・意味解釈 | 本文を取得できる場合の初期必須処理から外す案 |
| フォルダ内全資料の一括取込み | 維持しつつ、必要なファイルだけの選択を追加する案 |
| 画像のGemma読取・複数方式OCR | 消さずに補助経路へ。後述の範囲・期限で必要時だけ使用する案 |
| 同一画像の再利用 | 先行実装を利用。初見画像の高速化とは別に扱う |

### 現時点で確認した実装事実

- `Probe.extract_docx/extract_xlsx/extract_pptx`にnative本文・セル・表・位置・構造関係の抽出がある。PDFの`read_pdf_snapshot_page`も使える。ただしPDFの文字列抽出は、表の行列が正しく復元できたという保証ではない。
- 現行`extract_pdf`はnative文字があるページも画像化する。`deferred_per_document`は文書終了前に画像観測を完了させる方式で、全資料の本文だけを先に利用可能にするものではない。
- `suppressed`は子画像処理の内部制御で、高速モードではない。OCRやOCR空時のGemma転記が別に走り、画像意味未読の記録も自動で付くわけではない。`allow_vlm=False`だけでも全視覚経路は止まらない。
- 現行adapter等は未完成の`in_progress`成果を公開しない。ここを緩めず、読取方針・未読範囲を明示した「本文・表フェーズの完成世代」を作る必要がある。
- 基礎索引の公開後に資料横断の意味グラフ補佐を作る経路は存在する。全補助グラフの完成を質問開始の必須条件へ追加しない。
- 視覚再利用の実測は、同一画像2回が137.14秒→70.94秒。初見1回は約70秒。これは1画像の観測であり、全体速度や正答率の保証ではない。

## 3. 提案する利用仕様

### A. 読む範囲を先に絞れる

アプリで「ファイル1つ」または「フォルダ」を選び、取り込むファイル一覧を確認して開始する。フォルダの一部だけにも絞れる。AIが重要そうな資料だけを無断で選ばない。

例：業務資料1冊で十分ならその1冊。店舗案内全体が必要なら対象フォルダ。選択外の資料を本文検索・画像探索・新版採用で黙って混ぜない。PC全体の新版候補検出は既存の別機能として扱う。

対象ファイル一覧・hash・選択範囲・読取方針・採用版を世代に結合する。質問に年度がなければ、その対象で確認できた現行資料を使い、未確定の版競合は既存の人確認へ。単に最大年や更新日時を選ぶ仕様へ変えない。

### B. まず本文・表を取得する

| 資料 | 初回に読むもの | 初回に一律には行わないもの |
| --- | --- | --- |
| TXT／Markdown／Word | 本文、見出し、箇条書き、表、脚注等の取得可能な原文と位置 | 挿絵・写真全部の意味推論 |
| Excel | シート、セル、行列見出し、単位、注記、結合セル等の対応 | 埋込画像全部の意味推論 |
| PowerPoint／ローカルに書き出されたスライド | 文字・表・取得可能なノート・スライド順 | 全スライドの画像化とGemma精読 |
| 文字を取得できるPDF | ページ本文と位置。読み順・表の対応に不安がある箇所を記録 | 文字がある全ページへのOCR／Gemma二重読取 |
| スキャンPDF／画像だけのページ | 所在・ページ・周辺情報と「文字未取得」の記録 | 検索準備を止めて全ページを精読すること |

PDF表の列が崩れる、文字が化ける、図だけに注記がある場合は「正しく取得済み」と扱わない。Excelの式と保存値も混同しない。文字数が多いだけで読取成功にしない。

本文・表から、資料→見出し→段落、表→行→セル、見出し→値、出典等の**明示された関係の地図**を作る。主語・担当者がない資料でも登録できる。「誰が／いつ／次に」専用の枠へ全資料を押し込めない。意味上の因果や行動主体は、資料にないものを補ってEdgeにしない。

### C. 本文・表の準備ができたら質問できる

単に処理途中の索引を公開するのではなく、対象全体の本文・表フェーズについて検査を通した完成世代を、既存の原子的な切替で公開する。

画面は「本文・表：質問できます」「追加読取が必要：○ページ／○画像」「読取失敗：○件」を分ける。後回しを失敗扱いにせず、逆に全読取完了とも表示しない。画像だけで本文を取得できていない場合は、利用できる本文がないことを明示し、対象ページを読む導線を出す。

画像の補完を行う場合も、結果を稼働中の索引へ直接追記しない。出典・hash・読取契約を検証した別の完成世代として切り替える。変更・再開時に旧対象や旧版で代答しない。

### D. 普通の質問を普通の検索で解決する

```text
質問と対象・採用版の確認
  → 本文・表から候補を検索
  → 原文の前後、行列見出し、注記、既存の出典関係を添える
  → 足りない関係だけ既存グラフをたどって補う
  → Gemmaが根拠から回答 → 既存の根拠照合・監査 → 表示
```

意図が明瞭なら確認会話を毎回増やさない。どの資料・範囲・版を指すかで答えが変わるときだけ一問確認する。

通常検索で候補が見つかっても、質問に必要な条件・例外が届いたとは限らない。見出し、同じ表の列名、脚注、前後段落を原文束として保ち、根拠を短く切りすぎない。LLMで全資料を事前要約し直す方式は採らず、要約を原文の代替根拠にしない。

「通常RAGを基本」は既存QF1の初回回答前の原文束・出典関係の補佐を撤去する意味ではない。既存の質問グラフ／検索／監査を保持し、毎回重い全資料グラフ探索や新しい監査を追加しない。既存の処理順を動かす必要が出たら、その差だけを別途説明・確認する。グラフ有無ではなく、回答・出典・時間で評価する。

### E. 画像を読むのは関連する箇所が必要なとき

初期リリースの第一判定は本文・表だけで行う。画像補完はその合格後の次段階とし、最初の速度改善の成否判定を待たせない。

補完条件：文字未取得の関連ページ、表の対応が崩れた箇所、本文の「図参照」、画像・配置自体を尋ねる質問、回答に必要な例外が未読部分にある可能性。検索語がヒットしないだけで「図にも答えがない」とは言わない。候補はファイル名・見出し・ページ等から絞り、絞れなければ全フォルダ精読へ広げず一問確認する。

補完はまず必要ページのOCR。画像の意味・配置が必要な場合だけ既存Gemma観測へ。既存の確度区分を維持し、単独の暫定読取を確定根拠へ格上げしない。画像補完が動かない／使えないことを、本文で答えられる無関係な質問の停止理由にしない。

候補上限案は1質問につきOCR対象2ページ、意味精読1画像、同じ未変更入力への自動再試行0回。実行前に残りの時間枠を確認し、検証済み監査を省いて帳尻を合わせない。現行180秒/画像等の保護上限は引き上げない。上限外は対象・理由・追加の待ち時間を示して利用者に戻す。これは提案値で、実装前のカードで確定する。

## 4. 速くするために落とさない精度条件

- 数値、単位、年齢境界、曜日、時間、禁止・例外、担当、手順順序、出典位置を保持する。検索対象を削る場合も、関連する見出し・条件・注記を一緒に扱う。
- 未読の図があっても、必要範囲を確認できた個別の事実は答える。一方、関連範囲を確認できていないのに「全部」「存在しない」「最も」「これで手順完了」と断定しない。
- ページ・表・画像ごとに「本文取得済／OCR暫定／追加読取待ち／読取失敗／非対応」を区別し、検索・回答・監査・画面まで伝える。関係があるか不明なら不明とする。全資料の画像未読を一律の回答拒否にしない。
- 回答できない理由を「資料の記述が曖昧」「関連部分をまだ読んでいない」「抽出・検索・生成・検証の処理失敗」「対象範囲で確認したが根拠不足」に分ける。原文が曖昧な場合は該当箇所を見せる。
- 原文・根拠のない回答、旧版との混在、安全判定の迂回を速度と引き換えに通さない。正しく答えられる質問の過剰保留も品質上の不合格として数える。
- Gemmaのモデル入替え、入力容量縮小、引用検査の削除、新しい多重監査、SemIf/Jev再導入、クラウド利用は本計画に含めない。

## 5. 速度と品質の受入目標案

以下は未測定の設計目標であり、現在達成している速度ではない。モデル導入時間は通常利用と分離するが、通常利用に必要なモデル読込・埋込・監査時間は隠さず計測する。

| 場面 | 目標案 |
| --- | --- |
| 本文・表中心の代表資料1冊 | 選択確定から初回質問可能まで3分以内を目指す |
| 本文中心の小フォルダ | 5分以内を目指す。ファイル数・ページ数・セル数・容量を固定して比較 |
| 直接的な事実質問 | 根拠・監査を含む最終回答を60秒程度、まず90秒以内を比較目標 |
| 手順・条件分岐・複数根拠の質問 | 3分を目指し、従来の実用目標3〜5分に収める |
| 画像補完が必要 | 追加処理を表示。合計5分の実用枠に収まる見込みがなければ、自動追加せず継続判断へ |

性能目標と既存の強制timeoutは別物。既存timeoutを勝手に短縮／延長しない。質問の5分枠を制御へ接続する場合は、既存期限・監査に必要な時間との整合を確認してからカード化する。

準備時間は「本文抽出／OCR／意味観測／地図・検証／埋込・索引／公開」、質問時間は「検索／関係補完／生成／監査／表示」に分けて計る。モデル呼出回数・入力／出力量、初回か再利用か、処理失敗も記録する。初回画像を省いても埋込・検証等が律速になる可能性があるため、画像だけが原因と決めつけない。

### 品質の試験セット

既存約10問の受入を捨てず、計20問程度へ整理する。本文・表・手順・資料横断12問、図だけに答えや例外がある4問、曖昧さ／根拠不足／処理失敗／版競合4問を目安とする。実資料にない問題は、原資料を改変せず別の合成資料を使う。

DAWNの既存の稼働時間・料金・注意・手順、ルフルティエの住所・来店手順を候補に含め、別業務・主語のない資料・新しい質問でも試す。正解文の丸暗記ではなく、質問が求める必須事項・根拠位置・許される留保を試験前に固定する。正解表は索引やモデル入力へ混入させない。採用版は試験時に明示する。

回答は人が確認できる形で、実用回答／誤答／正当な保留／過剰保留／処理失敗／出典不一致と所要時間を記録する。20問の結果から一般正答率95%や100%を主張しない。既存受入の誤答を許容するよう基準を下げず、全保留による見かけの安全性も合格にしない。

## 6. 実装の進め方：先に小さく可否を判定する

| 工程 | 作業と出口 |
| --- | --- |

| **判定点** | 同じ必要事項と出典を保持し、初回準備が実用目標へ近づくか確認。速くならない・読み落とすならここで止めて原因と採否を提示。新機能を足し続けない |

R1–R2の小比較は改善前4問＋改善後4問、準備は前後各最大1回を初期上限案にする。同じ資料hash・モデル・設定・Readerの既存測定が使えれば、改善前を長時間再実行せず記録を利用し、その測定日時と条件を明示する。不具合修正後の比較は同じ合格条件で1巡まで。上限に達したら結果を報告し、勝手に実験数・モデル・対象を増やさない。R4の約20問はR2の効果確認後に進む。繰返しの速度測定はR4で代表2問を各計3回までに限定し、中央値・最大値を併記する。少数試行を統計的な品質保証とはしない。

## 7. 実行者向けの変更候補と接続上の注意

以下は調査済み候補であり、現時点での編集許可一覧ではない。各工程開始前に、必要なスキーマ・検証器・テストを含む正確なファイル集合をカードへ固定する。後から黙って対象追加しない。

- Reader：`scripts/probe_intermediate_records.py`、`scripts/build_intermediate_records.py`、`scripts/local_image_ocr.py`。本文先行モードと未読範囲の明示、OCR転記と意味VLMの両方の起動制御。
- 接続：`scripts/build_search_units.py`、`scripts/adapt_layer1_to_local_memory.py`、`distribution/macos-local-memory/engine/build_adaptive_semantic_graph.py`。原文・構造・未読範囲を欠落させず接続。
- 読取契約：既存`schemas/document.schema.json`等を変更するのか、独立したcoverage成果物を世代へ結合するのかをR1で決める。どちらもschema・validator・adapter・索引・実行時読取の検証を一体で対象にする。`in_progress`の公開許可へすり替えない。
- 世代：`distribution/macos-local-memory/app/bootstrap.py`の`run_semantic_pipeline`／`write_reader_generation_contract`／`build_index`、engineの`build_local_semantic_index.py`。読取方針・対象範囲・未読範囲をfingerprint/世代契約へ固定。既存の版・安全partition・原子的公開・中断復旧を保持。
- 入口・回答：同`app/source_selection.py`、`app/local_memory_server.py`、`engine/answer_local_memory_v2.py`。候補選択と未読状態をつなぐ。`intent_contract.py`、`claim_graph_validator.py`、`final_answer_audit.py`は再利用が基本。未読範囲を渡す変更が必要ならその接続だけを明示し、監査方式自体の研究へ広げない。
- 試験：既存Reader／PDF／取込再開／版切替／workflow／intent／source-selection試験を維持。新しい本文先行・coverage契約の合成試験と、実UIの初回導線を追加。静的試験・mock成功を実Gemmaの受入に代用しない。
- 既存のVLMスプールは文書終了時に消す一時物で、後日の精読待ち保存へ流用しない。再読は、元資料のhash・所在・ページ／画像位置を確認して安全に再取得する。変わっていたら同じ資料の続きとして扱わない。

## 8. 変更承認と戻し方

- 今の方式：本文・表に加えて画像も先に広く読み、準備する。既存の方式自体は残す。
- 変えたいこと：本文・表の完成世代で先に質問可能にし、画像の未読を明示して必要箇所だけ補完する。ファイル単位でも選べる入口を用意する。
- 理由と影響：文字中心の資料の準備待ちを短くできる見込み。画像だけの情報は初回から使えないことがあり、追加読取または保留が発生する。速度は小比較で確かめる。
- 変更しない場合：既存方式と同一画像再利用は使えるが、初見画像の広範な先行処理が残る。
- 戻し方：既存app・設定・索引世代・Reader方式を保持した別候補で検証。新方針を無効化して既存方式へ戻せるようにする。安全契約の異なる世代を混ぜたり、失敗時に旧対象を自動採用したりしない。

次の承認単位はR1–R2の小比較。今回の計画依頼を実装・実資料の再取込・本番更新の許可へ拡張しない。未達なら数値と残件を提示し、「使う範囲を限定する／追加修正する／中止する」を利用者が選べる状態で止める。
