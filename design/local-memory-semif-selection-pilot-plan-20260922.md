## 2. 何を試すか

「読む順番」は、利用者に見せる回答文の順序ではなく、**Gemmaへ渡す根拠資料の束の優先順**を指す。見せ方の変更は今回の対象外。

|用途|SemIfに選ばせること|選ばせないこと|
|---|---|---|
|読む順番|どの原文の束を先に読めば、質問の要件を確認しやすいか|必要な資料の削除、唯一の正解資料の認定、最新版の承認|
|重点確認|誰が・条件・順序・数値・対象範囲のどこを先に確かめると役立つか|回答の最終合否、監査の省略、人の意図や資料にない関係の確定|

回答は引き続きGemmaが作る。選択結果は未検証の補助であり、原文根拠より上位の指示にはしない。既存の検索・グラフ照合・版確認・必須監査は変えない。

重要な前提：原文量も監査回数も同じなら、順番を変えるだけで計算量が減るとは限らない。期待する効果はまず「一回で必要事項を押さえやすくなること」。速度はモデル読込・切替を含めて別途測定し、追加処理で遅くなる可能性も評価する。

## 4. 第1段階：選択だけを安く試す

実験案ID：CR-SEMIF-SELECTION-01。実行は承認待ち。

### 入力とケース

非機密の架空の備品管理・会議室利用・申請・保守など、カフェに特化しない短い日本語資料を新たに用意する。既存の実資料を再取り込みせず、旧10項目の丸暗記的な再試験にもせず、新しい16例で見る。

**読む順番：8例**

1. 必要な日時が一つの束にある。
2. 同じ単語があるが、質問と違う属性を説明した束が混ざる。
3. 担当名が似た別の仕事の説明が混ざる。
4. 本文に加え、例外・制限も読む必要がある。
5. 二つの束を合わせないと要件を満たせない。
6. 質問と資料で言い方が異なる。
7. 提示された範囲に必要情報がない。
8. 根拠が競合し、一つを優先して正解扱いしてはいけない。

入力は質問・要件・出典付き原文の束3件。見出しだけでなく、条件と周辺説明を含む原文を渡す。選択肢は3つの束IDと「一つを優先せず従来順を維持」の4つ。複数の束が必要な例では、最初に読むものとして妥当なIDの集合を事前定義する。競合や未発見では原則として従来順を維持し、情報不足の理由そのものをこの選択で確定しない。

選ばれた束だけを前へ出し、残りの束は従来の相対順で残す。束の内部の行・条件・原文順序は変えない。提示順を作業の時系列や優先順位の根拠と解釈させない。

**重点確認：8例**

1. 原文と候補回答で担当が違う。
2. 条件は候補回答の本文に正しく書かれているが、専用欄は空である。
3. 手順の順序が取り違えられている。
4. 上限・数値が取り違えられている。
5. 適用する対象や範囲が違う。
6. 正しく簡潔な回答で、特別な重点指定の必要がない。
7. 原文の主語が曖昧で、特定の関係を決められない。
8. 複数の重要な問題があり、一つに絞ると誤解を招く。

入力は質問・要件・原文全文・共通の候補回答。候補回答は模擬試験用として事前作成し、この段階でGemmaの生成は行わない。選択肢は「担当」「条件・制限」「順序」「数値」「対象・範囲」「重点を一つに定めず従来確認」の6つ。

「重点に選んだ＝そこが誤っている」ではない。正しく本文に書かれた重要な条件も重点になり得る。原文と質問から、先に確かめると役立つ観点を採点する。重点未特定は合格・回答可を意味せず、通常の確認を省略しない。

### 公平性と作業上限

- 8例×2用途×選択肢の順序2通り＝**最大32選択**。SemIfのロード1回、worker起動から終了までの外側上限600秒（資産検査・モデル読込・入力検査・32選択・結果保存を含む）、再試行0、Gemma生成0。親runnerが期限を管理し、モデル読込中の停止にも対応する。
- 元の選択肢順と逆順で同じ資料を試す。比較は表示位置・A/B記号ではなく、不変の候補IDで行う。原文の提示順はこの比較では固定し、二つの変更を混ぜない。
- 入力上限4096token。全件の長さを事前検査し、途中切捨て・勝手な容量拡張をしない。
- 既存SemIf `ca3ba65f142967030ecb453346e94d6f476a69df` と既存ローカルQwen3.5-4B `851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a` を使用。追加取得・量子化変更・共有状態の高速化実験はしない。
- 旧workerは4分類専用の検査を持つため、そのまま使えたことにはしない。承認後、新しい隔離フォルダに今回の可変候補ID・6択までを検査するrunner/worker/protocolとテストを作る。旧worker・旧ゲートは変更しない。
- 新workerにもオフライン強制・ネットワークソケット接続禁止・既存資産hash照合を引き継ぐ。tokenizerの`trust_remote_code=False`を維持し、モデル由来の未検証コードを実行しない。キャッシュ・一時ファイルを含む書込先は新しい隔離フォルダに限定する。親runnerの通信は既存localhostモデルの稼働状況確認だけで、外部送信や生成は行わない。
- 正解集合・原文に基づく採点理由・入力・プロンプト・呼出上限を実行前に固定し、別担当が読み取り点検する。結果を見た後に期待値や閾値を変えない。正解・採点理由・テスト目的を示すラベルをモデル入力に混ぜない。
- スコアは選択肢間の相対値として保存する。正答確率とは呼ばず、後付けの閾値で失敗を救済しない。
- 意味上の誤選択は実験結果として記録し、予定の32件を続ける。技術エラー、入力超過、資産差異、未登録ID、通信異常、時間超過は停止。空回答や失敗も消費済みとして記録し、成功まで繰り返さない。
- 他のモデルが稼働中なら開始しない。稼働アプリのモデルを勝手に止めない。同時ロードせず、実験workerの終了を確認する。

### 評価と次段階へ進む目安

用途別に次を出す。32選択を「独立した32問」とは数えず、16の元ケースと順序変化として集計する。

1. 原文・要件に対して有用な選択だったか。
2. 選択肢の順序を変えたときに、不適切な選択へ変わらなかったか。許容される候補同士の変化も別記する。
3. 明確な場合に「従来どおり」ばかり選んでいないか。
4. 該当なし・競合・曖昧さを、無理に一つへ結び付けていないか。
5. 選択時間、読込時間、検査・保存を含む全体時間、メモリを分ける。

暫定的な次段階候補の条件は、用途ごとに「両方の順序で適切だった元ケースが7/8以上」「明確に優先対象を定められるケースで、一度も不必要な従来維持へ逃げない」「必要根拠の削除・条件の欠落・未登録IDの採用が0」。これは少数試験を次へ進める目安であり、実用精度や本番採用基準ではない。

両方通った場合は、まず重点確認をGemma比較の候補とする。読む順だけよりも、追加ヒントがどの読み違いに役立ったかを観察しやすいため。片方だけ通ればその用途だけを候補にし、両方不十分なら止めて結果を説明する。成功例だけに絞った再試験はしない。

## 5. 第2段階：Gemmaに渡して本当に役立つか

第1段階の結果を確認してから、選ばれた用途の具体的な作業カードを提示する。以下は比較の設計方向であり、この計画作成や第1段階の実行許可だけで開始しない。

有望な**片方だけ**を、選択試験に使っていない新しい少数例で比較する。最初から両用途を同時投入して原因を分からなくしない。

|比較条件|内容|
|---|---|
|A：補助なし|同じ原文・質問・候補回答で従来の処理|
|B：一般的な助言だけ|「質問の要件に関わる条件や担当等を重点確認」とGemmaへ直接指示。追加モデルは使わない|
|C：SemIfの個別補助|Bと同じ指示に、選ばれた重点、または原文束の並べ替えを追加|

C対Aは補助全体の効果、C対Bは一般的な指示だけでは得られない追加価値を見る。読む順用途の場合も、Bは「要件に関わる原文を優先して読む」という固定指示に留め、Cとの差はSemIfが選んだ束を先に置くことだけにする。Cの良い結果だけで、すべての単純な並べ替え方式に優れるとは主張しない。

最小案は4つの新ケース×3条件。重点確認に候補回答が必要な場合、共通のGemma初稿をケースごとに一度作り、修正せず全条件へ渡す。事前に想定した誤りが出ない場合も記録し、苦手な出力が出るまで再生成しない。

具体カードでは使用中Gemmaの版・digest・context・出力枠・各呼出timeout、既存必須監査の回数k、補助を差し込む一箇所を読み取り確定する。概算呼出上限は12条件分の処理と対応監査12k、必要な共通初稿最大4回、SemIf選択4回。実際の現行経路が複数の生成を必要とする場合は、その全呼出を上限へ展開して**承認前に**提示する。上限を合わせるために既存工程を削らない。

全条件で同じ原文全文・必須監査・出力上限を保持する。順位の低い原文や非重点の観点を省略しない。Cのヒントを監査の正解として与えず、最終回答は原文から点検する。群の実行順をケースごとに変え、ロード済み状態やキャッシュの有利不利を記録する。

見るものは、要件を満たした初回回答数、条件・担当・例外の保持、誤回答、適切な保留、不必要な保留、不要な確認や修正の数、および実際に計測できた区間の時間。人の出戻り減少は、単回比較だけでは実測したことにしない。

SemIfまとめ実行の平均時間と、一問ごとにモデルを切り替える実利用の時間は別物。同時常駐はしない。まとめて実験する場合は品質比較までとし、アプリの高速化とは言わない。速度が有望なら、後続の限定した連続実行で、初稿・SemIfロード・選択・解放・Gemma再ロード・回答・既存監査を含む該当経路を測る。初回とロード済み条件も分ける。

CがBと同程度なら「SemIfではなく固定した助言だけで十分」という結論も成功した検証として受け入れる。Bより品質が上がっても遅ければ、その交換条件を示す。品質低下を速度で自動的に正当化せず、最終的な採用は人に戻す。両用途の併用・本番組込みはさらに別判断とする。
