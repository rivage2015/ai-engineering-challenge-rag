## 1. 人間向けの要約

同じ質問・資料・Gemmaの初稿に対して、次の3通りで見直した回答を比べる。

|条件|見直すGemmaに渡す補助|分かること|
|---|---|---|
|A：追加ヒントなし|共通の見直し指示だけ|見直すだけでも直るか|
|B：普通の注意書き|A＋担当・条件・順序・数値・範囲を確認する一般的な助言|追加モデルなしで十分か|
|C：SemIfの個別ヒント|B＋SemIfが選んだ確認観点1件|普通の助言を超える効果があるか|

主比較は**C対B**。Aは補足的な対照。CとAだけを比べてSemIfの価値としない。

任せる候補は「ここを注意して読んで」というヒントだけ。正解判定、資料の削除、矛盾の決着、最新版の承認は任せない。Gemmaが回答を作り、別の呼出しで原文から最終監査する。ヒントは最終監査へ渡さない。

まず架空の新規4例で、**明確な場面で役立つか／苦手な場面で邪魔しないか**を見る。普通の注意書きと同じ結果なら、SemIfを追加する効果は未確認とする。

## 4. 現行コードをどう扱うか

読み取り確認：`distribution/macos-local-memory/app/final_answer_audit.py` の `audit_fail_closed()` → `audit()` は、固定回答・原文を別コンテキストで監査する**1回のHTTP呼出し**。同関数内の再試行はない。

ただしアプリ全体には、項目監査・機械検証・条件付き再監査等がある。したがって、**本番アプリ全体の必須監査回数をk=1とする計画ではない**。

今回切り出す境界は「事前に全原文を渡した短い質問の初稿→見直し→通常の最終監査1回」。検索・資料取り込み・質問グラフ・資料グラフの効果は測らない。本体の処理順も変えない。本番の監査を省略した簡易版として本番合格を宣言しない。

最終監査は既存の通常SCHEMAと `audit_fail_closed()` を利用する。`workflow_groups` 専用の別契約へ切り替えて出力枠を増やすことはしない。本番モジュールの編集はしない。実験用の通信wrapperで、宛先・モデル・回数・期限・keep_alive・生出力保存を制御する。監査プロンプト・SCHEMA・既存の終了/容量/整合検査は保持する。

今回の4例は簡単な「手順」の問いとして作り、現行正規表現の通常手順監査に該当させる。送信前に監査payloadがcontext8192・出力1000・temperature0・think:falseになることを、実通信をしないcaptureテストで確認する。`workflow_groups` / `workflow_explanations` がなく、通常SCHEMAそのものと一致することも検査する。容量だけを確認して別経路を通したことにしない。不一致を黙って書換えない。

## 5. 4例の構成と、採点を先に決める方法

全て架空・非機密・カフェ非特化。質問・要件・原文・出典ID/path/locator・正解に必要な事実・許容する保留と理由を、初稿生成前に固定する。

|ID|題材と狙い|原文の状態|期待する読み方|
|---|---|---|---|
|N1|設備の点検依頼を提出する手順。受付担当と作業担当を区別|提出先が明記されている|質問が求める担当を取り違えない|
|N2|備品の持出し手順。利用条件と禁止例外|条件と例外が明記されている|本文の条件も読み、専用欄の有無だけで判定しない|
|N3|研修申込みの手順と料金|申込手順はあるが、提示原文に料金記載なし|手順は答え、料金は今回の提示範囲では未確認と理由付きで区別|
|N4|会議室の取消手順と締切|同じ対象・時点の締切が競合し、優先する版情報なし|共通手順は答え、競合箇所の原文を示して締切を断定しない|

N4は**競合**に固定する。「複数の重要点があるが原文に矛盾はない」という別ケースまで検証済みとしない。4例だけで全担当・全条件・全業務を網羅したとも言わない。

- 一例の原文は1〜3束。短くするために条件や例外を削らず、最初から短い架空の原文を書く。
- 4例はSemIfに見せる前・Gemma生成前に独立した読取レビューを受ける。
- 各例について「全要件を満たす答え」「正当な部分回答・保留」「不正確な断定」「不必要な保留」の基準を別goldに記録する。gold・狙いのラベルはモデルへ渡さない。
- 初稿は各例一回だけ。間違えなかった、期待した間違い方でなかった、という理由で生成し直さない。初稿を人が書換えて誤りを仕込まない。
- 全条件で同一の初稿・質問・要件・原文全文・出典を使用。Aの回答をBへ、Bの回答をCへ渡さない。

## 6. 実行順と各条件の差

1. オフラインの入力・期待値・プロンプト・検査コードを点検してhash固定する。初稿・ヒントは、その入力から一意に参照される実行時出力として追記hash管理する。
2. Gemmaで4例の共通初稿を各1回生成し、生出力と時刻・使用量を保存する。初稿は未監査であり利用者への業務回答として採用しない。
3. Gemmaの解放を確認してから、SemIfを1回ロードし、質問・要件・全原文・未修正初稿から重点を各1回、計4回選ばせる。既存の6候補ID（担当/条件/順序/数値/対象範囲/default）と説明を固定して使う。
4. SemIf worker終了と解放を確認する。Gemmaで各例のA/B/Cを見直す。順序はN1=A/B/C、N2=B/C/A、N3=C/A/B、N4=A/C/Bと固定する。各見直し直後に、その回答だけを別コンテキストで最終監査する。
5. 12の見直し回答と監査結果を、条件名を伏せた対応表で原文・goldに照合する。別担当が意味評価を照合し、不一致は勝手に正解扱いせず原文付きで残す。

共通の見直し指示：元の質問の要件と原文に照らして初稿を確認し、必要なら修正して回答する。原文にない情報を補わない。本文・条件・否定・担当・出典の対応を保持し、分からない部分は理由と該当原文を示す。内部思考過程ではなく利用者向け回答を返す。注意先候補が付いていても未検証であり、原文より優先しない。候補が示す観点が誤りだという意味ではなく、他の観点の確認も省略しない。

Bだけに足す一般助言：『質問で求められた担当・条件・順序・数値・対象範囲を重点的に確認してください。本文にある条件も読み、全ての原文・確認観点を残してください。』

CはBと同じ文章に、選ばれた候補IDと固定説明だけを追加する。全条件の入力に同じ `attention_hint` 欄を持たせ、A/Bはnull、Cだけ選択IDと固定説明（defaultならnull）とする。上のヒントへの注意文は全条件に共通なので、Cだけに別の安全助言を追加しない。B/Cの送信内容の差はこのヒント欄だけであることを機械検査する。

**不適切なヒントも修正・取り消さずにCへ渡す。** 人が正解ヒントへ交換しない。相対スコアで採否閾値を作らない。最終監査にはSemIfヒントもA/B/Cラベルも送らず、元の質問・見直し回答・原文で点検する。

SemIfの選択肢順は今回1通りで固定する。前試験で見つかった順序への弱さを解決したとは言わない。順序別の追加実験・複数候補選択は含めない。

- `audit_fail_closed()` は技術失敗を例外ではなく `status="incomplete"` / `performance.failed=True` として返すことがある。このどちらかが立っていれば、verdictがrejectedでも意味上の不合格として続行せずrunを停止する。通常の完了したrejectedと区別する。
- SemIfの意味上の誤選択、Gemmaの完了した誤回答・不必要な保留・監査誤判定は観測結果として残し、計画した比較を続ける。技術異常や保護違反は止める。

入力検査は、監査・生成ごとに送信本文UTF-8バイト数＋wrapper余裕512＋出力予約をcontext以内に収める保守的検査と、返却usage/終了理由/SCHEMAを組み合わせる。これは正確な入力token計測や全原文理解の証明ではない。SemIfはtokenizerで全4件を4096以下と確認してからモデルをロードする。

生成16Kで完成しても、長い回答が後段監査8Kに収まる保証はない。実際の回答を含めた入力検査で超過したら、その時点で技術停止する。成功させるための原文や回答の切捨て・再生成・枠拡大はしない。

見込みは隔離実装・機械検査・レビュー・実推論・報告で**1〜2.5時間程度**。未計測の新ワークフローなので概算であり保証ではない。モデル実行は上の固定上限で管理する。

## 8. 評価と終了条件

各例・各条件で、見直し回答をまず原文から採点し、監査結果とは別に記録する。『監査がverifiedと言った』だけでは正解にしない。

1. **要件充足**：求められた情報を全て正しく答えたか。資料不足・競合では、答えられる部分と理由付き保留を適切に分けたか。
2. **原文忠実性**：担当・条件・否定・例外・数量・適用対象を保持したか。資料にない断定がないか。
3. **監査の適切さ**：誤った断定を通さず、正しい回答や適切な保留を不当に落としていないか。理由と未支持主張が実際の本文/原文に対応するか。
4. **不要な出戻りの兆候**：初稿が正しいのに見直して誤ったか、普通の助言では不要だった確認・不回答が増えたか。人の実利用での出戻り削減を測定済みとしない。
5. **時間と資源**：初稿、SemIf読込/選択/解放、見直し、監査を分ける。load・prompt_eval・eval・全体時間と観測可能なメモリを保存する。

次の研究を検討する暫定条件（本番採用条件ではない）：

- Cは、原文に忠実で要件を満たし、監査も適切だった例をBより少なくとも1例増やす。
- 4例それぞれで、Bより要件充足・原文忠実性・監査の正しさのいずれも悪化しない。別例の改善で危険な悪化を相殺しない。
- Cの根拠のない断定・重要な条件/担当の欠落・誤答の監査通過が0。N3/N4では正当な部分回答・保留を維持する。
- 全原文・出典・全確認観点が保持され、技術停止や比較入力の差異がない。

同点は追加価値未確認。Bが全例正しければ天井効果として記録し、勝ちが出るまでケースを追加しない。CがBより良くても遅ければ、その交換条件を示し自動採用しない。Cの回答が正しくても監査で落ちる場合は、利用者が答えを得られる状態に改善したとはしない。

一回の4例では一般正答率・95%精度・統計的優位を主張しない。明確な2例と境界2例を分けて報告し、『得意な場面の自動検出ができた』としない。意味評価が割れた項目は理由と原文を示し、確定した勝ちに数えない。

このまとめ実験の所要時間を、アプリの一問あたり短縮時間に換算しない。実利用ではモデル切替が増えるため、品質に追加価値が見えた後でのみ、別承認の連続経路計測を検討する。
