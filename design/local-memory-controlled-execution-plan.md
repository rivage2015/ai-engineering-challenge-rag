## 1. 実行者への必須指令

**実行計画は必ず守ってください。変更する場合は、実行前にユーザーへ分かりやすく変更点を説明し、明示的な承認を得てください。**

「こちらの方が効率的」「精度が上がりそう」「依存箇所を先に直すべき」「テストが通る」「寝ている間に進めてと言われた」は、計画外の変更を許可する理由ではない。提案と実行を分ける。

このルールはSolに限らず、全モデル、サブエージェント、長時間実行、再開、別スクリプトに適用する。ユーザーの新しい具体的な指示で変更された場合は、その内容と範囲を記録する。上位の安全・権限指示には引き続き従う。

## 2. 守る構想

### 本体の役割

1. 指定・許可されたローカル資料から、原文根拠と資料の関係を保持する。
2. まず通常RAGで必要な根拠を探す。
3. 通常RAGで不足する場合、質問の対象・条件・関係をノードとエッジとして整理し、資料側グラフの関係をたどって根拠を集める。
4. ローカルGemmaを使い、原文と出典に基づいて回答する。グラフの見た目の類似だけで正解とはしない。
5. 資料の版や質問意図を決められない場合はHuman in the Loop。読めない部分は読めないと説明する。

これはユーザーが再確認した目標構想。復元済みコードが完全にこの順番で動くという確認ではない。復元版には通常検索前のQuestion Evidence Graph処理と、従来回答後の補助意味グラフ処理がある。どちらをどう整えるかは、差分を説明して承認を受ける別作業であり、本書の作成をもって変更してよいことにはしない。

「不足」の判定条件、グラフの適用範囲、失敗時の戻り方も実装前の説明対象。Gemmaの自己申告の確信度だけで判定を固定しない。根拠の競合・版未確定・権限問題を、別経路で答える口実にしない。

### 受賞者の知見の位置付け

- 資料目録・出典付き用語集：候補を探す補助。要約を回答根拠にせず原文へ戻る。
- 見出し・表・書式の保持：本体が使う情報を落とさないための読取補助。
- 限定的な再読：不足した箇所の原文根拠を補う。無制限の調査や独立した回答器にしない。

いずれも採用候補。受賞者のシステム全体、クラウド依存の自律調査、全質問へのグラフ強制、大量の確認・監査の追加を一括導入しない。補助機能OFFで本体が動くことを比較する。ただし、原資料の改変・矛盾・未承認版を見つけた場合は、既存の安全判定を迂回して古い回答を返さない。

原文と解釈の分離、出典位置、ローカル完結、原本保護、版確認は維持する。開発にChatGPTを使うことと、アプリが外部LLMへ資料を送ることを混同しない。

## 3. 自走できる範囲／事前承認が必要な変更

| 承認済み作業カードの中で自走できること | 変更説明と承認が必要なこと |
| --- | --- |
| 対象ファイルの調査、定めた修正、定めた範囲のテスト | 目的、アーキテクチャ、検索順、グラフの役割、入力・出力の意味の変更 |
| 外部挙動を変えない変数名・関数内の整理 | ファイル・資料・索引・UI・依存ライブラリ等の対象追加 |
| 同じ仕様を確かめる、許可されたテストファイル内の試験追加 | 合格基準や期待する根拠の変更、テスト削除・skip化、安全検査の緩和 |
| 既に許可された上限内での試験と、進捗記録 | 順序依存・段階・予算・再試行上限の変更、実験を本番へ昇格 |

試験の失敗を理由に仕様や正解を変えない。試験自体に誤りがあった場合も、根拠を示して変更承認を受ける。「付随修正」「前提整備」「一時的な最適化」と呼び替えて範囲外へ進まない。

調査・説明だけの依頼には、その目的に必要な読み取りを行える。実装用カードを理由に、単純な質問への回答まで毎回承認待ちにしない。

## 4. 編集前に作業範囲を固定する

実装を求められたら、1作業単位のカードを提示する。既にユーザーが具体的に指示した項目は再承認を求めず、その指示を承認根拠として記録する。足りない決定だけを一つずつ確認する。

```text
作業ID／使用する計画の版：
目的：利用者に何ができるようになるか
承認根拠：ユーザーの発言と対象範囲（提案文や監査PASSを承認にしない）
変更対象：具体的なファイル。生成物は用途と出力先を限定する
変更しないこと：検索順、原資料、本番索引など
検証・合格条件：どの質問・根拠・挙動がどうなるか
作業上限：承認された試行回数・時間等。制約がある場合は省略しない
戻し方：既存資産を保持して戻す方法
状態：提案中／承認済み／実行中／承認待ち／完了
```

変更ファイルの全体像が不明なら、まず読み取り調査で対象を絞る。空欄・未承認のカードを実装許可と解釈しない。コードの局所的な実装詳細は、既定範囲内なら担当者が決めてよい。

## 5. 計画変更の確認は、専門用語ではなく利用者の変化で説明する

変更したいときは、該当部分の作業を止め、次の形で説明する。通常は短い箇条書きで済ませ、必要な詳細だけ補足する。略語だけで説明しない。利点だけでなく不利益・不確実性も示す。

```text
承認待ち：変更案 CR-001（対象の作業ID）
・今の予定：何をする約束だったか
・変えたいこと：変更前 → 変更後
・理由：確認できた不具合や制約。事実と予想は分ける
・あなたへの影響：答え方、待ち時間、確認回数、資料の扱いはどう変わるか
・変えない場合：できること／できないこと。現計画を維持する選択も示す
・変更範囲と戻し方：どこを変更し、どう元に戻せるか
質問：この変更だけを行ってよいですか？
```

説明例（提案の例であり、承認済みではない）：

> 今は、普通の検索で足りないときだけグラフを使う予定です。変更案では毎回グラフを使います。複雑な質問に役立つ可能性はありますが、簡単な質問も待ち時間が増える可能性があります。これは当初の方針を変えるため、まだ実装しません。この変更をしてよいですか？

### 承認の扱い

- 一度に確認する変更は一つ。別々の判断が必要な変更を、まとめて「改善してよいか」と聞かない。
- ユーザーの明示的な返答と対応する変更案ID・範囲を記録してから、計画の次版と作業カードへ反映する。AI自身で`approved`を作らない。
- 直前の単一・具体的な変更案への「それでよい」は承認として扱える。決まった合言葉を要求しない。何へのOKか不明なら確認する。
- 無回答・不在・別件へのOK・以前の自走依頼は承認ではない。明示された条件付き承認の条件を省略しない。
- 承認待ちの変更と、それに依存する作業は開始しない。独立した承認済み作業だけは続けてよいが、その範囲を報告する。
- 「ひとまず試す」ための変更版の実行・別環境への実装も、計画外なら承認前に始めない。読取調査や差分案の説明はできる。
- この承認ルール、AGENTS.md、本書、合格条件を緩める変更も同じ手続きを通す。後から計画を書き換えて逸脱を正当化しない。

## 6. 実行・再開・引継ぎでのチェック

1. 作業開始時にAGENTS.mdと本書、最新のユーザー指示、作業カード、未解決の変更案を読む。承認が記録と会話で一致しなければ読み取り確認に留める。
2. 開始時のGit差分を確認し、ユーザーの既存変更と自分の作業を区別する。旧checkpointの「次へ」を最新の許可として使わない。
3. 編集前に作業ID・対象・合格条件を短く報告する。実行中は実行中、ユーザー判断待ちは承認待ちと明示する。
4. 作業単位の後に、変更済み・未追跡・生成ファイルと挙動をカードへ照合する。`git diff --check`やファイル差分確認は補助であり、構想への一致まで自動証明しない。
