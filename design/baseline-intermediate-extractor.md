# 基礎中間データ抽出器 v0.2

## 目的

診断用の少量プローブを、任意のルート配下へ同じ規則で適用できる基礎抽出器へ
進めた。質問、record ID、案件名、正解候補を参照せず、対応形式と原本構造だけで
処理する。

この段階では回答RAGへ接続しない。抽出漏れや容量を確認してから、検索用派生データを
別工程で作る。

## 実装

### ビルドCLI

`scripts/build_intermediate_records.py`

- `--root`配下からDOCX、XLSX、PPTX、PDFを再帰発見する。
- `--input`を指定した場合は、任意の明示ファイルだけを同じ処理で抽出する。
- Officeの一時ファイル`~$...`は除外する。
- 診断用の葉要素上限を使用せず、現在対応している要素を全件出力する。
- 1ファイルの解析失敗をDocumentの`failed`状態として残し、既定では次のファイルへ進む。
- 出力先が原本ルート内にある場合は拒否し、自己取り込みを防ぐ。
- 出力先が空でない場合は拒否し、既存の抽出結果を無断で上書きしない。

### 共通レコード処理

`scripts/probe_intermediate_records.py`のレコード生成部を診断・全件の両モードで
再利用できるようにした。

- 診断モード: 葉要素上限あり、回答用索引への利用禁止を警告する。
- 全件モード: 上限なし。ただし形式別の未対応構造をDocumentの`partial`警告へ残す。
- extractor名とversionをRelationの安定IDへ含める。

`scripts/validate_intermediate_records.py`は、Relation自身のprovenanceからgenerator名と
versionを取得してIDを再計算するため、診断版と基礎抽出器の両方を検証できる。

## 共有ドライブの規模

全416ファイル、約227MBを確認した。基礎抽出器の直接対応対象は、一時ファイルを除いて
119ファイルである。

| 形式 | 件数 |
|---|---:|
| DOCX | 46 |
| XLSX | 20 |
| PPTX | 25 |
| PDF | 28 |

CSV、JSON、Markdown、Python、Notebookなどは、別のテキスト・コード抽出器として
追加する。現時点のビルドCLIは、それらを黙ってメタデータだけにせず対象外としている。

## 全件モード検証

各形式から小さい実ファイルを1件ずつ選び、葉要素上限なしで2回生成した。

| 検査 | 結果 |
|---|---|
| 入力 | DOCX、XLSX、PPTX、PDF各1件 |
| Document | 4 |
| Evidence | 436 |
| Relation | 436 |
| 抽出失敗 | 0 |
| 必須項目、内容ハッシュ、安定ID | 合格 |
| 原本サイズ、原本SHA-256 | 合格 |
| 親子参照、Relation端点 | 参照切れ0件 |
| 同一時刻での2回実行 | 3つのJSONLすべてバイト単位で一致 |
| 既存出力の上書き防止 | 合格、終了コード1で拒否 |

## 大規模XLSX検証

4シート、ピボット、グラフ部品を持つXLSXを上限なしで処理した。

| Evidence種別 | 件数 |
|---|---:|
| worksheet | 4 |
| table_cell | 130,438 |
| pivot_table | 2 |
| chart | 9 |
| 合計 | 130,453 |

Relationも130,453件生成し、全検査に合格した。3つのJSONL合計は約179MBだった。
この結果から、セルをそのまま1 Evidenceずつ保存すると原本サイズより中間データが
大幅に増えることが分かった。

## 現在の`partial`理由

- DOCX: ヘッダー、フッター、コメント、run単位の書式spanが未完。
- XLSX: 高度なOOXMLオブジェクトとグラフ参照元の対応付けが未完。
- PPTX: スピーカーノートとグループ図形内部の抽出が未完。
- PDF: ページ内text block、画像、領域座標の分離とOCRが未完。

対応済み要素は全件出すが、未対応部分がある間はDocumentを`success`にしない。

## 判断と次の工程

基礎抽出器の全件モード、失敗記録、安定ID、参照整合性、上書き防止は成立した。
一方、大規模XLSX 1件だけで約179MBになるため、共有ドライブ119件の一括生成はまだ行わない。

JSONLのストリーミング書き出しとファイル単位の再開機能は、
`design/streaming-resume-extractor.md`に記録した。

次は、セルEvidenceをそのまま全件検索へ投入せず、表領域・行・意味単位へまとめる
検索用派生層を設計する。

これにより、原本事実を失わずに保持する層と、RAGで高速に検索する層を分離する。
