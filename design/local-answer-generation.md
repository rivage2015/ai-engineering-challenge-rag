# APIキー不要のローカル回答生成

## 目的

共有ドライブの未加工データと質問文だけを入力にし、検索結果から最終回答を自動生成する。
特定の質問、案件、ファイル名、正解、ページ番号、セル番地による専用分岐は持たない。

参加・提出を優先する最初の経路では、既存の全資料抽出キャッシュとBM25検索を使い、
回答生成だけをローカルOllamaへ切り替える。新しい中間データ・ハイブリッド検索は、
全資料対応後に同じ回答生成インターフェースへ接続する。

## 実装

- 既定バックエンド: `ollama`
- 既定モデル: `qwen3.5:9b`（通常回答）
- 保留モデル: `gemma4:12b`（難問・監査の比較用）
- 外部APIキー: 不要
- 温度: `0`
- seed: `42`
- Ollamaコンテキスト: プロンプト量に応じて `8K / 16K / 32K / 65K`を自動選択
- 並列数: ローカル実行は既定 `1`
- 1問の生成タイムアウト: 既定180秒。停止した問は「わかりません」として次へ進む
- 途中保存: 問ごとにローカルcheckpointへ保存し、同じ条件の再実行時に自動再開
- 回答方針: 検索資料だけを根拠に簡潔に回答し、根拠不足なら「わかりません」
- ログ: モデル、バックエンド、検索上位資料、回答、実行時間を保存
- ハイブリッド検索: BM25とローカル意味検索を2レーンで同時実行後、従来と同じRRFで統合

Ollamaのreasoning対応モデルでは、最終回答ではなく`message.thinking`だけで生成上限へ
達する場合がある。そのため最終回答の再現性と速度を優先し、`think=false`を全問共通で
指定する。これは質問内容によらない生成設定である。

コンテキスト長は従来の`65536`固定ではなく、ASCIIと日本語の概算トークン数に、
回答上限と安全余白を加えて最小の段階を選ぶ。長い証拠入力は`32K`または`65K`へ
自動昇格させるため、通常質問のメモリ使用量を減らしつつ従来の最大入力経路を保持する。

2026-08-24の同一10問グラフ回答比較では、`qwen3.5:9b`と`gemma4:12b`の
最終CSVは一致し、厳密一致はどちらも9/10（同じ1問が表記差）だった。
実行時間は84.8秒対119.9秒で、Qwen経路が約29%短かったため通常回答の既定にした。

OpenAI APIを利用できる環境では、`RAG_BACKEND=openai`とモデル名を明示すれば従来経路も
使用できる。バックエンドの違い以外は同じ検索結果と回答プロンプトを使う。

## 2026-08-13 動作確認

正解付き30問を、汎用経路を変更せず最後まで実行した。厳密文字列一致は9問、
「わかりません」は10問、残る11問は表記差または誤答候補だった。画像・書式情報が
既存キャッシュにない問題では安全に棄権し、抽出済みテキストやコードの問題では
正答できることを確認した。

検証問題の正解や参照箇所は、コード、プロンプト、設定へ反映していない。
書式問題は個別対応せず、新しい中間データ抽出器の汎用的な書式抽出で対応する。

## 実行

```bash
ollama list
rag/.venv/bin/python rag/main.py --valid --start 0 --limit 1
rag/.venv/bin/python rag/main.py --valid
rag/.venv/bin/python rag/main.py
python scripts/validate_submission.py \
  --questions share/質問回答/questions_test.csv \
  --predictions rag/out/predictions.csv
```

`--limit`を指定した診断実行では、誤提出を避けるためZIPを作らず
`rag/out/predictions_preview.csv`だけを出力する。
